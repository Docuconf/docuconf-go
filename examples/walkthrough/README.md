# Walkthrough: from a Go struct to a validated Deployment

One service, `orders-api`, from its config struct to a running pod, on each
of the three platform paths docuconf supports: the `docuconf` CLI, plain CUE
(what a Crossplane composition function evaluates), and Helm.

Every file under `out/`, and `contract.cue`, `platform/tax_rates_schema.cue`
and the chart's generated files, is produced by [`run.sh`](run.sh). CI
re-runs it and fails if anything changes or the three paths disagree, so
what you read here is what the tools do today.

```
config/config.go          the app's config struct (Go SDK)
contract.cue              1. what the SDK exports
platform/values.yaml      2. what the platform supplies in production
platform/files.yaml          where each file input comes from
platform/prod-policy.cue     the platform team's own rules
platform/bad-*.yaml          the same, with mistakes
platform/deployment.cue   3. the platform in plain CUE (Crossplane path)
chart/                    4. the same service as a Helm chart
out/                      captured output of every step
```

## 1. The app declares its configuration

The app keeps its normal [caarlos0/env](https://github.com/caarlos0/env)
struct. docuconf's tags add what the platform needs to know: secrets,
constraints and file inputs. ([`config/config.go`](config/config.go))

```go
type Config struct {
	// Primary Postgres connection string.
	DatabaseURL string `env:"DATABASE_URL,required" secret:"true" schemes:"postgres,postgresql"`

	// Kafka brokers orders are published to.
	Brokers []string `env:"KAFKA_BROKERS,required" minItems:"1"`

	// Timeout for calls to the payments service.
	PaymentsTimeout time.Duration `env:"PAYMENTS_TIMEOUT" envDefault:"5s" min:"100ms" max:"30s"`

	// Certificate the API serves HTTPS with.
	TLS docuconf.TLSKeyPair `file:"serving-tls,required" path:"/etc/orders/tls" reload:"watch" dnsNames:"orders.internal" minRemaining:"720h"`

	// Tax rates by country, loaded at boot.
	TaxRates docuconf.ConfigFile[TaxRates] `file:"tax-rates,required" path:"/etc/orders/tax/rates.yaml"`
	// ... PORT, LOG_LEVEL, TRACE_SAMPLE_RATIO
}
```

`docuconf export` turns it into a CUE contract. This is the only thing the
app hands the platform, and it is the same shape whichever language SDK wrote
it ([`contract.cue`](contract.cue), abridged):

```cue
// Code generated by docuconf. DO NOT EDIT.
package orders

import "docuconf.dev/contract"

contract.#Contract & {
	apiVersion: "docuconf.dev/v1alpha1"
	kind:       "ConfigContract"
	metadata: {name: "orders-api", appVersion: "2.3.0", generator: {language: "go", sdk: "docuconf-go", version: "0.1.0"}}
	vars: {
		DATABASE_URL: {
			type:        "url"
			description: "Primary Postgres connection string"
			required:    true
			secret:      true
			schemes: ["postgres", "postgresql"]
		}
		KAFKA_BROKERS: {type: "list", description: "Kafka brokers orders are published to", required: true, items: "string", encoding: "csv", separator: ",", minItems: 1}
		PAYMENTS_TIMEOUT: {type: "duration", description: "Timeout for calls to the payments service", default: "5s", min: "100ms", max: "30s", encoding: "go"}
		// ...
	}
	files: {
		"serving-tls": {type: "tls", description: "Certificate the API serves HTTPS with", required: true, secret: true, path: "/etc/orders/tls", reload: "watch", dnsNames: ["orders.internal"], minRemaining: "720h"}
		"tax-rates": {
			type: "config", format: "yaml", required: true, path: "/etc/orders/tax/rates.yaml"
			description: "Tax rates by country, loaded at boot"
			// JSON Schema generated from the Go type TaxRates.
			schema: {
				type: "object"
				required: ["default", "countries"]
				additionalProperties: false
				properties: {
					default: {type: "number", description: "Rate used when a country is not listed", minimum: 0, maximum: 1}
					countries: {type: "object", additionalProperties: {type: "number"}}
				}
			}
		}
	}
}
```

Two details matter downstream. `encoding: "csv"` and `encoding: "go"` tell the
platform how this app parses lists and durations, so the platform writes them
in that form. `schema` is generated from the Go type the file is decoded
into, so the platform checks the file against the type the app actually uses.

## 2. The platform supplies values, and the CLI checks them

The platform team writes the environment's inputs as typed data, not
strings ([`platform/values.yaml`](platform/values.yaml),
[`platform/files.yaml`](platform/files.yaml)):

```yaml
# values.yaml
DATABASE_URL:
  secretKeyRef: {name: orders-db, key: url}
KAFKA_BROKERS: [kafka-0.kafka:9092, kafka-1.kafka:9092]
PAYMENTS_TIMEOUT: 2s
LOG_LEVEL: warn
TRACE_SAMPLE_RATIO: 0.05

# files.yaml
serving-tls:
  certificate:
    name: orders-tls
    secretName: orders-tls
    dnsNames: [orders.internal]   # resolved from the cert-manager Certificate
    duration: 2160h
    renewBefore: 720h
tax-rates:
  inline:
    default: 0.2
    countries: {DE: 0.19, FR: 0.2, IE: 0.23}
```

and its own rules, which apply to every service whether or not the app knows
about them ([`platform/prod-policy.cue`](platform/prod-policy.cue)):

```cue
LOG_LEVEL?:          "info" | "warn" | "error"   // no debug logging in production
TRACE_SAMPLE_RATIO?: <=0.1                       // trace at most 10% of requests
```

```console
$ docuconf vet -contract contract.cue -values platform/values.yaml -files platform/files.yaml -policy platform/prod-policy.cue
orders-api: ok
```

With [`bad-values.yaml`](platform/bad-values.yaml) and
[`bad-files.yaml`](platform/bad-files.yaml), every problem is reported at
once, before anything reaches the cluster ([`out/vet-bad.txt`](out/vet-bad.txt)):

```console
$ docuconf vet -contract contract.cue -values platform/bad-values.yaml -files platform/bad-files.yaml -policy platform/prod-policy.cue
DATABASE_URL: is secret, so it must come from a secretKeyRef, never a literal or another reference
KAFKA_BROKERS: is required, and set neither by the platform nor by the selected profile
LOG_LEVL: is not declared in the contract (check the spelling)
PAYMENTS_TIMEOUT: "2 seconds" is not a duration such as 1m30s
PORT: 80800 is above max 65535
TRACE_SAMPLE_RATIO: 1.5 is above max 1
TRACE_SAMPLE_RATIO: 1.5 is not allowed by policy
serving-tls: certificate does not cover orders.internal
serving-tls: certificate renewBefore 240h is less than minRemaining 720h, so the app could see a certificate with too little time left
tax-rates: inline content does not match its schema: default: invalid value 20 (out of bound <=1)
```

The database password in the bad file (`mysql://orders:hunter2@...`) appears
in no output; `run.sh` checks that.

`docuconf render` turns valid inputs into the pod's configuration
([`out/render.yaml`](out/render.yaml)):

```yaml
env:
  - name: DATABASE_URL
    valueFrom:
      secretKeyRef: {name: orders-db, key: url}
  - name: KAFKA_BROKERS
    value: kafka-0.kafka:9092,kafka-1.kafka:9092      # the app's csv encoding
  - name: LOG_LEVEL
    value: warn
  - name: PAYMENTS_TIMEOUT
    value: 2s                                         # the app's Go duration encoding
  - name: TRACE_SAMPLE_RATIO
    value: "0.05"
volumes:
  - name: dc-serving-tls
    secret: {secretName: orders-tls, defaultMode: 256}   # 0400
  - name: dc-tax-rates
    configMap:
      name: orders-api-tax-rates-3be5cf588e              # hash of the content
      defaultMode: 292                                   # 0444
      items: [{key: rates.yaml, path: rates.yaml}]       # projected, never subPath
volumeMounts:
  - {name: dc-serving-tls, mountPath: /etc/orders/tls, readOnly: true}
  - {name: dc-tax-rates, mountPath: /etc/orders/tax, readOnly: true}
configMaps:
  - apiVersion: v1
    kind: ConfigMap
    metadata: {name: orders-api-tax-rates-3be5cf588e}
    immutable: true
    data:
      rates.yaml: |
        default: 0.2
        countries:
          DE: 0.19
          FR: 0.2
          IE: 0.23
restartTriggers: []      # serving-tls is reload: watch, so rotation needs no restart
```

## 3. The same thing in plain CUE (the Crossplane path)

The CLI is a thin wrapper around the CUE meta-schema. A platform built on
Crossplane and CUE uses the meta-schema directly: the contract, the
environment's values and the policy unify, and if they don't, there is no
Deployment ([`platform/deployment.cue`](platform/deployment.cue), abridged):

```cue
package platform

import (
	"docuconf.dev/contract"
	orders "docuconf.dev/orders"                 // the app's contract.cue
	policy "docuconf.dev/platform:policy"        // prod-policy.cue
)

_values: _ @embed(file=values.yaml)
_files:  _ @embed(file=files.yaml)
_values: policy                                  // platform rules on top

check: contract.#Validate & {
	"contract": orders
	values:     _values
	files:      _files
	#schemas: "tax-rates": #TaxRates             // the contract's JSON Schema, as CUE
}

_render: contract.#Render & {"contract": orders, values: _values, files: _files}

objects: [
	for cm in _render.configMaps {cm},
	{
		apiVersion: "apps/v1"
		kind:       "Deployment"
		spec: template: spec: {
			containers: [{
				name:         orders.metadata.name
				env:          _render.env
				volumeMounts: _render.volumeMounts
			}]
			volumes: _render.volumes
		}
		// ...
	},
]
```

`#TaxRates` is the contract's JSON Schema converted with
`cue import jsonschema:` ([`platform/tax_rates_schema.cue`](platform/tax_rates_schema.cue)):

```cue
#TaxRates: close({
	default!:   >=0 & <=1
	countries!: [string]: number
})
```

`cue vet -c ./platform:platform` passes, and
`cue export ./platform:platform -e objects` gives the ConfigMap and the
Deployment ([`out/cue-objects.yaml`](out/cue-objects.yaml)); `run.sh` checks
that its env, volumes, mounts and ConfigMaps equal `docuconf render`'s.

With the bad inputs, CUE refuses too ([`out/cue-vet-bad.txt`](out/cue-vet-bad.txt),
positions removed):

```text
check.fileChecks."serving-tls".coversDNSName."orders.internal": conflicting values false and true:
check.fileChecks."serving-tls".renewsBeforeMinRemaining: conflicting values false and true:
check.fileChecks."tax-rates".matchesSchema.default: invalid value 20 (out of bound <=1):
check.values.TRACE_SAMPLE_RATIO: invalid value 1.5 (out of bound <=0.1):
...
```

Raw CUE errors are correct but terse, and CUE stops at some errors before
it reports the rest (`PORT` and the `LOG_LEVL` typo are missing above).
That is why `docuconf vet` exists: it runs the same `#Validate` and turns
the result into one line per problem.

## 4. The same service as a Helm chart

For a platform on Helm, the chart carries the contract, and Helm itself
enforces it. One command writes what the chart needs:

```console
$ docuconf helm -contract contract.cue -chart chart
wrote chart/files/docuconf/contract.json
wrote chart/values.schema.json
```

The inputs go under `docuconf` in [`chart/values.yaml`](chart/values.yaml),
in the same shape as `platform/values.yaml` and `platform/files.yaml`:

```yaml
docuconf:
  values:
    DATABASE_URL:
      secretKeyRef: {name: orders-db, key: url}
    KAFKA_BROKERS: [kafka-0.kafka:9092, kafka-1.kafka:9092]
    PAYMENTS_TIMEOUT: 2s
    LOG_LEVEL: warn
    TRACE_SAMPLE_RATIO: 0.05
  files:
    serving-tls:
      certificate: {name: orders-tls, secretName: orders-tls}
    tax-rates:
      inline:
        default: 0.2
        countries: {DE: 0.19, FR: 0.2, IE: 0.23}
```

and the [Deployment template](chart/templates/deployment.yaml) includes the
[docuconf library chart](../../helm)'s helpers:

```yaml
          env:
            {{- include "docuconf.env" . | trim | nindent 12 }}
          volumeMounts:
            {{- include "docuconf.volumeMounts" . | trim | nindent 12 }}
      volumes:
        {{- include "docuconf.volumes" . | trim | nindent 8 }}
```

`values.schema.json` is generated from the contract, so Helm checks every
`helm lint`, `template`, `install` and `upgrade` against it
([`out/helm-bad.txt`](out/helm-bad.txt), entries sorted):

```console
$ helm template orders-api chart -f bad.yaml    # LOG_LEVEL: verbose, LOG_LEVL: warn, DATABASE_URL: mysql://...
Error: values don't meet the specifications of the schema(s) in the following chart(s):
orders-api:
- at '/docuconf/values': additional properties 'LOG_LEVL' not allowed
- at '/docuconf/values/DATABASE_URL': got string, want object
- at '/docuconf/values/LOG_LEVEL': 'anyOf' failed
  - at '/docuconf/values/LOG_LEVEL': value must be one of 'debug', 'info', 'warn', 'error'
  - at '/docuconf/values/LOG_LEVEL': got string, want object
```

A secret given as a literal fails, and Helm does not print it. The
`tax-rates` content is checked against the app's `TaxRates` type by Helm too,
because the file's JSON Schema is part of `values.schema.json`.

The rendered Deployment ([`out/helm.yaml`](out/helm.yaml)) has the same env,
volumes and mounts as `docuconf render`. One difference is expected: the
`tax-rates` ConfigMap is named `orders-api-tax-rates-737df012bb`, not
`...-3be5cf588e`. Helm writes structured content with its keys sorted
(`countries` before `default`), so the bytes and their hash differ while the
data is the same. Each path is consistent with itself; give the content as a
string if you need byte-identical output on both (SPEC §4.6.1).

### What Helm checks, and what it leaves to `docuconf vet`

JSON Schema covers types, ranges, patterns, enum values, URL schemes, list
bounds, required inputs, unknown names, secrets-only-as-references and
structured file content. It cannot compare durations (`PAYMENTS_TIMEOUT`
above `30s` is only caught by `vet`), know what a cert-manager Certificate in
the cluster covers, or apply a platform policy. Run `docuconf vet` in CI
before `helm upgrade` for those.
